01

What Sentry is and why we use it

One page, so you know what the app does before you press the first button.

Sentry is a desktop app that checks the quality of a software project with AI agents. You pick the project folder; the agents read the code on their own, plan checks, run real commands and tests, and return a list of problems they found — each one backed by evidence.

The problem it solves

Manual testing takes hours, and ordinary AI assistants often "find" problems that don't exist or miss the real ones. Sentry is built so that an agent can't just say "there is a bug here": every finding has to point to a specific file and line and be confirmed by a command the agent actually ran.

Independent agents

Five agents — OpenCode, DeepSeek, GLM, ChatGPT and Claude — work at the same time without seeing each other.

Evidence, not opinions

Every finding has a place in the code (file and line), a severity and evidence — the commands the agent ran and their output.

Safe for your project

The agents work on a copy of the project in an isolated Linux environment (WSL). Your original files are never changed.

How it works, in short

Who it is for

Developers and QA teams who want a quick independent check before a release; students who want to check their project before handing it in; teachers who grade many projects.

What you need

Windows 11 (64-bit), virtualization turned on, ~10 GB free space, internet and a key for at least one AI provider. Prepare WSL by hand before installing (chapter 2).

02

Installing

We recommend preparing WSL and Ubuntu by hand first. The setup wizard then does the rest.

Recommendation

Prepare WSL and Ubuntu by hand before running the setup wizard. The wizard can install them too, but this is the part that causes the most problems — most often creating the Linux user on Ubuntu's first start. By hand it takes about 10 minutes, you see every message from Windows and Ubuntu, and the wizard then detects that WSL and Ubuntu are ready and skips them.

Step 1 (recommended): prepare WSL and Ubuntu by hand

Run the commands in PowerShell. Where it says "as administrator", right-click PowerShell → Run as administrator.

  1. Check virtualization Open Task Manager → Performance → CPU. At the bottom it must say Virtualization: Enabled. If it says "Disabled", turn on Intel VT-x or AMD-V (SVM) in the computer's BIOS/UEFI.
  2. Install WSL as administrator 
    PS> wsl --install --no-distribution
# restart the computer, then:
PS> wsl --update
PS> wsl --status          # must say: Default Version: 2
  3. Install Ubuntu 
    PS> wsl --install -d Ubuntu
    On its first start Ubuntu asks for a user name (Enter new UNIX username). Use lower-case Latin letters, no spaces — for example ivan. Then type a password twice; nothing is shown while you type — that is normal. Close Ubuntu with exit.
  4. Check the result 
    PS> wsl -d Ubuntu whoami   # must be your name, not root
PS> wsl -l -v              # Ubuntu must show VERSION 2
    If the version is 1: wsl --set-version Ubuntu 2. If the answer is root, see chapter 11 before you continue.
Good to know

An Ubuntu you installed by hand stays yours: Sentry's uninstaller never offers to remove it.

Step 2: the setup wizard

Download SentrySetup-<version>-windows-x64.exe and double-click it. It installs for the current user, so it doesn't ask for administrator rights at the start.

Windows SmartScreen

If Windows shows "Windows protected your PC", click More info and then Run anyway. The warning appears because the file is not yet signed with a paid publisher certificate, not because it is dangerous.

  1. Choose the language — English or Bulgarian. The whole wizard and its messages use this language.
  2. OK — goes on to the welcome page.
  1. What gets installed — WSL2, Ubuntu, the Linux tools and the agents' tools. On a new PC it takes 10–30 minutes; Windows asks once for administrator approval and may need one restart.
  2. Next — to the next page.
  3. Desktop shortcut — leave it ticked if you want a shortcut on the desktop. A Start menu shortcut is always created.
  4. Install — starts the real work: the wizard shows 6 steps with plain messages.

The six steps after "Install"

  1. Checking the computerWindows 11, virtualization, free space (~10 GB).
  2. Installing WSL2One administrator approval; may ask for a restart.
  3. Installing UbuntuA Linux user is created with your name.
  4. Preparing the Linux tools
  5. Installing the Sentry runtime
  6. Installing the agents' tools
If the computer restarts

Sometimes Windows has to restart to finish WSL2. The wizard tells you, and once you sign in again it continues by itself from where it stopped. Finished steps are also skipped if you run the wizard again by hand.

At the end the wizard offers to open Sentry. A detailed log of every step is in %LOCALAPPDATA%\Sentry\logs\setup-wizard.log — the first place to look if something goes wrong (see chapter 11).

Uninstalling

Open Settings → Apps → Installed apps → Sentry → Uninstall. The uninstaller always removes the program, the shortcut and the sentry command, then asks up to three questions. All three default to "No", so you can't lose anything by accident:

QuestionIf you answer "Yes"When it appears
Also delete Sentry's data?Deletes projects, runs, findings, the agents' tools and saved keys.Always
Also remove Ubuntu?Deletes the whole Ubuntu distribution, including your own files in it. Cannot be undone.Only if Sentry installed Ubuntu
Also remove WSL?Removes WSL from Windows (asks for administrator approval).Only if Sentry installed WSL and no other distribution is left

04

Adding a project

A project is a folder of code. Sentry makes its own copy and works only on that.

  1. Add Project — opens the Windows folder picker. Choose the project's main folder (where package.json, pom.xml and so on live).
  2. Status — "Ready" once the copy is made and can be checked.
  3. Revision — the current version of the copy; the button next to it copies it.
  4. Runs — how many checks have been made on the project.
  5. Open — the project page (below).
  6. Remove project — removes the copy and its history from Sentry. Your folder is not touched.
Adding by path

If you prefer to paste a path, the ⓘ icon "Advanced: add by path" at the bottom right of the page opens a field for a full path (for example C:\Projects\online-shop) — press Enter.

The project page

  1. Name and path — where the project came from (the path as the Linux runtime sees it).
  2. Update Project — makes a new revision from the folder's current contents. Use it after every code change, before a new run.
  3. Remove project — as on the Projects page.
  4. Project state — whether the copy is ready. While a run is going, updating waits.
  5. Readiness — whether the project can be checked.
  6. Current revision — the newest copy.
  7. QA runs — number of runs.
  8. Tabs — Run QA (chapter 5), Findings (chapter 9), Setup (below) and Activity — the history of actions on the project.

Preparing the agents (the "Setup" tab)

  1. Project profile — per agent: "Build" makes the agent read the project and write a short description. Then turn on "Use project profile" when you start — runs begin better informed.
  2. Get to know the project (all agents) — the same for all agents at once.
  3. What this project's files ask for — tool versions written in the project itself (for example .nvmrc).
  4. Ask — the agent says what must be installed to run the tests. Nothing is installed automatically — you decide in Settings → Toolchains.
  5. Ask all agents — the same for all agents.

Both steps are optional and use provider budget.

05

Starting a QA run

Everything is set in the project's "Run QA" tab — from top to bottom, then one button.

Scope and agents

  1. QA mode — Full QA (the whole project) or Targeted QA (only paths you name). The difference is in chapter 7.
  2. Run depth — Fast or Full. The ⓘ icon explains the difference right in the app.
  3. Revision — which version of the project to check. The current one by default; an older revision is useful for comparison.
  4. Revision details — when it was made and whether it is current.
  5. Selected agent — green frame and dot. Click a card to turn it on or off.
  6. Agent not selected — will not take part. Every agent uses budget at its provider.
  7. Readiness — Ready (checked), Configured (has a key, not yet checked). An agent without a key can't be selected.
  8. Reasoning effort — how "long the model thinks"; changed in Settings → Providers.

Notes, options and start

  1. Different notes for each agent — turn on to give each agent a different task.
  2. Note for all agents — optional: what matters to you, for example "focus on payments". The agents read it while planning.
  3. Allow web access — the agents may open web pages. Off by default for stronger isolation.
  4. Use project profile — reuses the project description from an earlier run. "Unavailable" until a profile exists.
  5. Allow tool and SDK downloads — Sentry installs what is needed (Node, Python, Java…) so the tests can run.
  6. Check for secrets — adds the check for passwords and keys in the code (chapter 6). On by default.
  7. Packages & toolchains — explanation: installing the project's packages (npm, pip and so on) is always allowed; larger toolchains are managed in Settings → Toolchains.
  8. Summary — how many agents, which scope, and a reminder that it uses budget.
  9. Start — opens a confirmation window.
  1. Agents — who will work.
  2. Depth — Fast or Full.
  3. Revision — which version of the project.
  4. Network — what is allowed: ✕ off, ✓ on. "Packages" are always allowed — without them the tests can't run.
  5. Budget — the run costs real money or subscription quota.
  6. Start QA — starts the run and opens its page (chapter 8).
06

What an agent does during a run

The stages on the agent card, the rounds of the investigation and why each one exists.

Every agent follows the same path, independently of the others. The path is written into Sentry's code, not left to the agent: Sentry decides when each step starts, keeps the time and stops the agent when it goes in circles. The agent decides what exactly to check and how.

Before the agents start

  1. Frozen copy (snapshot)Sentry takes the selected revision and freezes it. Every agent checks exactly the same state, and your original stays untouched.
  2. Project profile optional
    If "Use project profile" is on, an agent reads the project once and writes a short description. Later runs use it and start faster.
  3. Packages & toolchains optional
    If "Allow tool and SDK downloads" is on, an agent lists what the project needs (for example Node, Python, Java), and Sentry installs it before the investigation so the tests can really run.

The seven stages on the agent card

Every agent card has a bar of 7 dots and a counter such as 4/7 Commands / Tests. The stages go in this order:

Evidence comes after the report, not before it: the agent sends its findings and evidence together with the report, and only then does Sentry check and store them.

Planning

The agent reads the project's documentation and source code without running anything. From that it builds three ordered lists — from the riskiest to the safest:

ListWhat it holdsExample from the demo project
Critical flowsThe main paths through the app that must work end to end.cart → discount → total
Weak pointsPlaces in the code that look fragile: complex logic, boundary values, comments saying "this can't happen".path check on export
ChecksConcrete yes/no questions. Each names a file, a function and the input that should break it."addItem with quantity 0, −1, 1.5"

Every critical flow gets at least one check that runs it with boundary values (zero, negative, empty, missing). The number of checks depends on the depth: Full — up to 8 (about one per 25 minutes of the time limit; 6 for 3 hours), Fast — up to 2. The plan is then frozen and doesn't change until the end — so the result is traceable.

▸ OpenCode is creating a frozen investigation plan.

The rounds of the investigation

After planning the agent investigates in rounds. Each round has its own goal, its own line on the card and its own limit. The diagram shows the whole path of a Full run; Fast stops after the second round.

Why Sentry runs the steps, not the agent

Left to decide when to stop, an agent often stops too early ("everything looks fine") or gets stuck on one check. So Sentry keeps the clock, the plan and the order of the rounds, and the agent is responsible for the investigation itself. That way two runs of the same project are comparable.

Every step — what it does and why

The last column is what you will see on the agent card at that moment (see chapter 8).

StepWhat it does and whyLine on the card
Checks (round 1)One turn per planned check. The agent writes a small probe (a test), runs it against the real code with a hostile or boundary input, and decides whether the check passed. Why: only a command that ran proves behaviour — reading is not enough.investigating check 3/6: …
Execution requiredIf the agent only read code for the check, Sentry makes it run a probe once. Why: without it, the check stays an opinion.(within the check)
Different approachIf the agent keeps repeating the same failing command or reads for too long, Sentry stops the turn and asks for another method — up to 3 tries. It is shown its failed commands so it doesn't repeat them. Why: agents sometimes go in circles.(within the check)
Time share reachedEvery check has a share of the total time. When it is used up, the agent writes down what it established without starting anything new. Why: the other checks and the report must fit.(within the check)
Check for secretsThe last check, if turned on: looks for passwords, API keys and tokens written straight into the code. Read only. Its result is the Secrets light on the card.investigating check 7/7: Secrets in code…
Second pass (round 2)Up to 3 checks that stayed undecided get another try in a fresh session — if at least 40% of the time is left. The agent sees what it already tried. Why: a decided check is better than "undecided" in the report.giving check 2 a second pass (1/3): …
Leads (round 3a)Up to 4 suspicious things the agent noticed outside its checks. Why: checks are narrow, and the real problem is often next to them.following up lead 1/4: …
Critical flows (round 3b)Up to 5 critical flows from the plan are run end to end, chaining the steps (the value from one step breaks the next). Why: finds bugs nobody suspected while reading.exploring critical flow 2/5: …
Deepening (round 3c)Up to 3 checks that passed quickly are attacked from new angles — other entry points, concurrency, failure and clean-up paths. Those with the least proof first. The earlier verdict stands unless a defect is found.deepening check 4 (1/3): …
Hazard sweep (round 4)Sentry itself scans the code for risky files — ones that delete files, rewrite paths or names, compare paths, parse text or hash content — ranks them, and the agent checks them one by one.running the hazard sweep (1/5): src/cleanup.js
ReportEverything is written into a report in a fresh session; 12 minutes of the time are kept for this. Every defect has a "Root cause" line — the file, the function and the logic that gives the wrong result.serializing the frozen investigation into a report.

The kinds of runs compared

Two independent choices — mode and depth — plus re-testing specific findings.

QA mode: what gets checked

Full QA

The agents get the whole project. Use it for a first check or before a release.

Targeted QA

You name paths (folders or files). The agents check only those and what they depend on — with the same depth. Use it after a change in one part of the project.

Depth: how thorough

Typical timeup to the limit (3 h by default)minutesminutes
When to use Fast

When you want a quick answer — after a small change, or to see how Sentry works. On the demo project a Fast run finished in under 3 minutes with 5 findings.

When to use Full

Before a release or a hand-in. Rounds 3 and 4 find problems nobody suspected. On the same demo project a Full run took 11 minutes and found 8 findings with 29 pieces of evidence, one of them critical.

Re-test

After fixing problems you don't need to run everything again. A re-test takes findings from an older revision and checks whether they are still there in the current one:

  1. Fix the code and press "Update Project"This makes a new (current) revision.
  2. Open the "Findings" tab and pick the older revisionTick up to 12 findings you want to check again.
  3. Choose who checks and press "Re-test N selected"The agent that reported each finding, or all selected agents. Confirm in the window.
  1. Re-test (3) — a tab in the agent's details, one row per finding.
  2. Passed — the problem is fixed. Here: the quantity rule and the single-use discount code, which we fixed in the code.
  3. Not passed — the problem is still there, with an explanation. Here: the API key, which we didn't touch.
  4. Summary — "2 resolved · 1 not resolved".
Good to know

A re-test finds no new problems and doesn't change the original findings — it only answers whether each one is still true. For new problems, start a new Fast or Full run.

The agent gets one question per finding — "is it fixed in this revision?" — and answers resolved, not resolved (and why) or "could not be determined". It looks for no new problems and doesn't change the original finding.

08

Following a run

The run page updates live — you see what every agent is doing right now.

  1. Kind and status — "Running", "Completed", "Failed" or "Cancelled".
  2. Cancel run — stops all agents. What was already found is kept.
  3. Results — number of agents, findings and evidence, updated live.
  4. Identifiers — the run and snapshot IDs. The button next to them copies them, for example for a bug report.
  5. Overview — mode, depth and time limit. The « button hides the panel and gives the canvas more room.
  6. Add-ons — which options are on: web access, downloads, secrets, profile.
  7. Project → Revision → Snapshot — where the code the agents check comes from.
  8. The agent card — one per agent (see below). Click it to see the details.
  9. Zoom — zoom in, zoom out, fit all (F) and re-layout. Cards can also be dragged.
  10. Details — the details of the selected card: overview, findings, activity, evidence, diagnostics.

The agent card

  1. Agent and model — which agent and which AI model it uses.
  2. Status and time — how long the agent has been working.
  3. The stage bar — 7 dots for the 7 stages (chapter 6). The yellow dot is the current stage.
  4. Stage — "4/7 Commands / Tests": how many stages are done and what the current one is called.
  5. The current step — what the agent is doing right now: which check, flow or file.
  6. Show more — appears when the step is longer than two lines.
  7. Findings and evidence — how much the agent has found so far.
"Show more"

The step description is often long — the agent names the file, the function and the input values it tries. "Show more" opens a window with the whole text of the step. The window keeps the step you clicked even after the agent moves on, and the Copy button copies the text. Close it with Close, Esc or a click outside it.

When the agent finishes

  1. Findings and evidence — the final count.
  2. Secrets — the light from the secrets check: green none found, red found, yellow not fully checked.
  3. The severity bar — the findings by colour: critical, high, medium, low. One look tells you whether anything is serious.
09

Results

What was found, how sure it is and how to export it.

Results appear in two places: in the agent's details on the run page (this run only) and in the project's Findings tab (all runs, grouped by revision).

The agent's details

Click the agent card. The panel on the right has several tabs:

If Developer mode is on in Settings → Application, there is also a Diagnostics tab with the technical details of the agent's run — useful if something went wrong.

The project's "Findings" tab

  1. Revision — whose findings to show.
  2. Re-test with — the agent that reported each finding, or all selected agents. Appears for an older revision (chapter 7).
  3. Re-test N selected — checks the ticked findings in the current revision.
  4. Export as — Markdown (a readable report), JSON (for scripts and other programs) or plain text.
  5. Export — only the ticked ones or all in the revision. The file is made without AI, nothing is sent anywhere and nothing is written into the project.
  6. The run — when, which kind, status; "Open run" goes to its page.
  7. Tick box — selects the finding for export or re-test.
  8. Severity — how serious the problem is (table below).
  9. Confidence — how well the problem is proven (table below).
  10. Title and place — what is wrong and in which file and line.

Severity

LevelWhat it means
CriticalData loss, a security breach, or a core flow broken for most users.
HighA main flow is broken or gives a wrong result for an ordinary input.
MediumWrong behaviour on a realistic edge case.
LowA cosmetic, rare or easily recoverable problem.
InfoA remark, not a defect.

Confidence

LevelWhat it means
ConfirmedThe agent reproduced the problem with a command.
StrongStrong evidence in the code, without a full reproduction.
ProbableIt looks that way but is not fully proven.
SpeculativeA suspicion worth checking by hand.
Before you fix

Findings are agent reports. They are backed by evidence, but review each one before changing the code — especially those with low confidence.

Exporting a whole run

On a finished run's page, top right, there is Export JSON (all the run's data — findings, evidence, stages) and Export log (the detailed log). They unlock once the analysis is done.

Settings and runtime

Four pages under "Settings" and one for the runtime's health.

  1. Providers — the agents' keys and models. Required before the first run.
  2. Runtime — which Linux distribution Sentry uses.
  3. Toolchains — languages and tools installed for the agents.
  4. Application — language, theme, time limit and more.

Providers

  1. Provider — for example OpenCode Go (monthly subscription), OpenCode Zen or OpenRouter (pay per use).
  2. Model — which AI model the agent uses. "Update list" fetches the newest models.
  3. API key — paste the key and press "Save". It is kept encrypted on this computer.
  4. Second key — for another provider, if you use one.
  5. Reasoning effort — higher is more thorough but slower and more expensive.
  6. Stop extra rounds when idle — the early stop from chapter 6. Off by default.
  7. Ready — the agent is checked and can be selected.

Application

  1. Appearance & Theme — dark, grey or light.
  2. Language — English or Bulgarian.
  3. Local CLI Broker — lets the sentry command in a terminal control the app.
  4. CLI command reference — downloads every command as a file.
  5. Confirm Before Paid QA Runs — the window from chapter 5. Leave it on.
  6. Developer mode — shows the Diagnostics tab and raw data.
  7. Run time limit — 3 hours (default), 6 hours, no limit or custom. It also sets how many checks a Full run plans.
  8. Note length limit — how long the note to the agents may be.

Runtime, WSL and toolchains

  1. Runtime health — whether the Linux runtime is connected and which distribution is used.
  2. Versions — Node, protocol and Sentry version in the runtime.
  3. Local CLI — whether the sentry command can connect.
  4. Ready agent — the key is saved, the program is present and the runtime is checked.
  5. Configured agent — has a key, but its runtime isn't tested yet. It is tested on the first run.
  1. Distribution — which Linux distribution Sentry uses. A change applies after the app restarts.
  2. Free up Windows disk space — gives back to Windows the space freed inside WSL (for example after removing projects). Nothing in use is deleted.
  3. Search — by name, version or purpose; "Installed only" hides the rest.
  4. Categories — languages, package managers, build tools, QA and security, databases… Open a category to install or remove a version.
  5. Custom add-ons — your own tool with your own install command.

When something goes wrong

Common problems, and what to do when Ubuntu opens as root.

What you seeWhat to do
Top right says the runtime is not connectedOpen Runtime from the left menu and see which check is red. It often helps to close Sentry, run wsl --shutdown in PowerShell and open Sentry again.
An agent is not "Ready", or its run fails at onceThe provider key is missing or wrong: Settings → Providers. Save the key and choose a model.
The agents can't run the tests (Node, Python, Java… missing)Turn on "Allow tool and SDK downloads" before starting, or add the tool in Settings → Toolchains.
A run takes too longChoose depth Fast or lower the time limit in Settings → Application. You can also cancel the run — partial results are kept.
Error SANDBOX_INIT_FAIL about "nested user namespaces"Ubuntu restricts nested user namespaces. In Ubuntu: sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0, then start again.
The setup wizard stops with an errorRead %LOCALAPPDATA%\Sentry\logs\setup-wizard.log. The most common cause is creating the Linux user on Ubuntu's first start — prepare WSL and Ubuntu by hand (chapter 2) and run the wizard again.

Ubuntu opens as root

First go through the manual preparation in chapter 2 — it fixes most WSL problems. If wsl -d Ubuntu whoami still answers root, creating the user failed. Fix it like this:

  1. Open Ubuntu as root 
    PS> wsl -d Ubuntu -u root
  2. Create the user and make it an administrator 
    # adduser ivan
# usermod -aG sudo ivan
# nano /etc/wsl.conf
    The file must contain these two sections (keep any other lines). Save with Ctrl+O, Enter and exit with Ctrl+X: 
    [boot]
systemd=true

[user]
default=ivan
  3. Restart Ubuntu and check 
    # exit
PS> wsl --terminate Ubuntu
PS> wsl -d Ubuntu whoami   # must now be your name
  4. Finish installing Sentry Run SentrySetup.exe again. It detects that WSL and Ubuntu are ready, skips those steps and goes on with the Linux tools, the Sentry runtime and the agents' tools.
Warning

Don't run wsl --unregister Ubuntu if Ubuntu holds your own files — it deletes the whole distribution without asking. It is useful only for a freshly installed Ubuntu that doesn't start properly: delete it and install it again (chapter 2, step 1).

12

Glossary

The terms you will meet in the app.

Agent
An AI model (OpenCode, DeepSeek, GLM, ChatGPT, Claude) that checks the project on its own, in its own isolated environment.
Provider
The service that supplies the agent's model (for example OpenCode Go). Keys are entered in Settings → Providers and stored encrypted.
Project
A folder of code added to Sentry. Sentry keeps its own copy; the original is not changed.
Revision
One state of the project's copy. "Update Project" makes a new revision from the folder's current contents.
Snapshot
The frozen revision the agents check during one run.
Run (QA run)
One check of the project by one or more agents.
Check
One concrete question from the agent's plan, answered with a probe that ran: passed, failed or undecided.
Frozen plan
The plan made during planning. It doesn't change until the run ends.
Critical flow
A main path through the app that must work end to end (for example "cart → discount → total").
Weak point
A place in the code that looks fragile when read, so it gets a check.
Lead
Something suspicious noticed outside the checks. In a Full run it is followed up in round 3.
Hazard
A file Sentry flags by itself: it deletes files, rewrites paths, compares paths, parses text or hashes content.
Finding
A problem found: title, description, severity, place in the code and evidence.
Evidence
A command that ran and its output, which confirm the finding.
Severity
Critical, high, medium, low or info — how big the problem's impact is and how easily it is reached.
Secrets
Passwords, API keys and tokens written straight into the code. The Secrets light is green (none), red (found) or yellow (not fully checked).
Project profile
A short description of the project, written once by an agent and used by later runs.
Full / Targeted QA
The whole project, or only chosen paths and what they depend on.
Full / Fast
The depth: all rounds, or only the checks and the second pass.
